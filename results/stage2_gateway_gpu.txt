Stage 2b: vLLM behind the LiteLLM gateway on a Colab T4
Run 2026-10-27, Tesla T4, vLLM 0.32.0, LiteLLM 1.90.2 (pip, same version as the Docker image).
Code: colab/gateway_gpu.py with this repo's litellm/config.yaml. Raw numbers: stage2_gateway_gpu.json.

What was run
  vLLM and the gateway on the same Colab runtime. The gateway used the repo's config file
  unchanged, so qwen3-gpu was routed by the same entry the Compose stack uses.
  tests/test_gpu.py through the gateway: 2 of 2 pass (answers; thinking off by default).
  The same question straight to vLLM and through the gateway gave 32 tokens both ways,
  so the gateway passes the thinking-off setting on and both routes do the same work.
  Then the stage 7 load test (same prompt, 32 tokens, 1 to 64 users) four times: direct and
  gateway in round 1, gateway and direct in round 2, so neither route always went first.
  4,320 requests in all, 0 errors.

  No degradation by the stage 7 rule on any of the four curves.

What it means
  With one or two users the gateway costs nothing measurable. From 4 users it adds about
  30 to 70 ms to a typical answer and takes 6 to 11% off throughput.
  The bigger effect is on the slowest answers. Their extra wait grows with the number of
  users, to almost half a second at 64. The median barely moves, so most requests pass
  straight through and a few wait behind others inside the gateway.
  On the CPU stack this cost was invisible, because each answer took seconds. On a GPU the
  model answers in about 0.6 s, so the gateway becomes a visible part of the total.

Likely cause, not measured
  The gateway ran as a single process here. Every request goes through it for the key
  check, routing and metrics, so under heavy load some requests queue there. Running more
  gateway processes is the usual fix for that; it was not tested.

Limits
  Master key only: Colab has no database, so per-user keys (a database lookup per request)
  were not in the measured path. The Compose stack would add that.
  Gateway and vLLM shared one machine, so they competed for its CPU. On separate machines
  the gateway's cost could be lower.
  The vllm service in docker-compose.yml has not been run under Compose. The laptop has no
  NVIDIA GPU and Colab has no Docker.

Problems hit getting it to run (fixed in colab/gateway_gpu.py)
  python -m venv failed on Colab: its Python has no ensurepip. virtualenv works.
  The pip package litellm[proxy] does not include prometheus_client, which the Docker image
  has and the config's Prometheus callback needs. The gateway crashed at start until it was
  installed: "ModuleNotFoundError: No module named 'prometheus_client'".
  When the gateway failed to start, the script left vLLM running and holding the GPU. The
  script now stops both servers however it ends.
